Ты работаешь над существующей БД упражнений для фитнес-приложения.

Твоя задача — провести полный аудит и подготовить точечные исправления существующей БД.

КРИТИЧЕСКИ ВАЖНО:

Мы НЕ создаём БД с нуля.
Мы НЕ переписываем все упражнения заново.
Мы НЕ меняем корректные данные без причины.
Мы НЕ удаляем данные только потому, что они отличаются между файлами.

Основная задача — привести существующую БД к согласованному состоянию, сохранив максимум уже корректных данных.

==================================================

1. РАБОЧИЕ ФАЙЛЫ
   ==================================================

Используй следующие файлы:

1. `final2DB-equipment-patched.json`
   Главная текущая БД упражнений.
   Это основной файл, который в итоге должен быть исправлен.

2. `05-equipment-v2-corrected.json`
   Актуальный справочник оборудования.
   Это канонический источник оборудования.

3. `06-exercise-equipment-v3-corrected.json`
   Актуальный источник связей:
   упражнение ↔ оборудование.

4. `03-taxonomy.json`
   Канонический источник taxonomy:
   категории, паттерны движений, сложности, мышцы, теги и другие допустимые значения.

5. `04-exercises.json`
   Исходный справочник упражнений.
   Используется как дополнительный источник для проверки и восстановления данных упражнений, но НЕ должен автоматически заменять данные из `final2DB-equipment-patched.json`.

6. `08-injury-warnings.json`
   Источник связей упражнений с предупреждениями/травмами.

ВАЖНО:

`final2DB-equipment-patched.json` — основной объект редактирования.

Остальные файлы используются для проверки, валидации и восстановления отсутствующих связей/данных.

==================================================
2. ПРИОРИТЕТ ИСТОЧНИКОВ
=======================

Используй следующий порядок при разрешении конфликтов.

ОБОРУДОВАНИЕ:

`05-equipment-v2-corrected.json`

имеет приоритет над любыми названиями оборудования в других файлах.

СВЯЗИ УПРАЖНЕНИЙ С ОБОРУДОВАНИЕМ:

`06-exercise-equipment-v3-corrected.json`

является каноническим источником этих связей.

TAXONOMY:

`03-taxonomy.json`

является каноническим источником допустимых значений taxonomy.

ТЕКСТ И УПРАЖНЕНИЯ:

`final2DB-equipment-patched.json`

является основным источником текущих данных.

`04-exercises.json`

используется для сравнения, проверки и восстановления отсутствующих данных, но НЕ для массовой замены текущей БД.

INJURY:

`08-injury-warnings.json`

используется как источник связей упражнение ↔ injury/warning.

==================================================
3. ГЛАВНЫЙ ПРИНЦИП
==================

Не исправляй данные только потому, что они отличаются от старого файла.

Сначала выясни:

1. является ли значение действительно неправильным;
2. есть ли каноническое значение в актуальном справочнике;
3. можно ли доказать правильное значение из файлов;
4. не является ли отличие просто допустимым вариантом.

Если нельзя уверенно определить правильное значение:

НЕ ДОДУМЫВАЙ.

Пометь проблему как:

`needs_review`

==================================================
4. ЧТО НЕЛЬЗЯ ДЕЛАТЬ
====================

Запрещено:

* менять UUID существующих упражнений;
* менять UUID оборудования;
* массово пересоздавать упражнения;
* массово переписывать названия;
* удалять упражнения;
* удалять оборудование;
* удалять существующие связи без доказанной ошибки;
* создавать новое оборудование, если подходящее оборудование уже есть в `05-equipment-v2-corrected.json`;
* создавать новые taxonomy values;
* создавать новые injury types;
* придумывать отсутствующие связи;
* заменять хорошие пользовательские тексты;
* переписывать упражнение полностью из `04-exercises.json`;
* считать старый `04-exercises.json` более актуальным, чем `final2DB-equipment-patched.json`.

Любое изменение должно быть точечным и иметь причину.

==================================================
5. EQUIPMENT
============

Для каждого упражнения из `final2DB-equipment-patched.json` проверь:

* `equipment_strings`;
* оборудование, упомянутое в `technique`;
* оборудование, упомянутое в `settings`;
* соответствующие записи в `06-exercise-equipment-v3-corrected.json`.

Затем проверь оборудование по:

`05-equipment-v2-corrected.json`.

Нужно найти:

1. оборудование используется, но отсутствует в `equipment_strings`;
2. оборудование указано, но не используется;
3. используется неканоническое название;
4. есть дубликаты названий оборудования;
5. equipment string не существует в актуальном equipment справочнике;
6. связь отсутствует;
7. существует неправильная связь;
8. есть связь с несуществующим equipment.

ВАЖНО:

Если в тексте встречается:

"конус"

а в `05-equipment-v2-corrected.json` существует каноническое оборудование "Конус",

использовать именно каноническое название.

Если в справочнике оборудования такого объекта нет — НЕ заменять его автоматически на случайное оборудование.

В таком случае:

`needs_review`

==================================================
6. ПЕРЕНОС EQUIPMENT RELATIONS
==============================

`06-exercise-equipment-v3-corrected.json` является каноническим источником связей.

Для каждого упражнения:

1. найти его связи в `06-exercise-equipment-v3-corrected.json`;
2. проверить существование exercise UUID;
3. проверить существование equipment UUID;
4. сопоставить equipment UUID с `05-equipment-v2-corrected.json`;
5. сравнить с `equipment_strings` в `final2DB-equipment-patched.json`.

Если связь существует в актуальном файле связей, она должна быть перенесена/сохранена в итоговой БД.

Если связь отсутствует в `final2DB-equipment-patched.json`, но существует в актуальном `06-exercise-equipment-v3-corrected.json`:

добавить связь.

Если связь существует в итоговой БД, но отсутствует в актуальном `06-exercise-equipment-v3-corrected.json`:

НЕ удалять её автоматически.

Сначала определить, действительно ли она ошибочна.

Если доказательств недостаточно:

`needs_review`.

==================================================
7. TAXONOMY
===========

Проверить все упражнения по `03-taxonomy.json`.

Проверяем:

* category;
* movement_pattern;
* difficulty;
* primary_muscles;
* secondary_muscles;
* tags.

Любое значение должно существовать в taxonomy.

Если значение отсутствует в taxonomy:

1. найти очевидное каноническое соответствие;
2. если соответствие однозначно — предложить точечную замену;
3. если соответствие неоднозначно — `needs_review`.

НЕ создавать новые taxonomy values.

==================================================
8. ВАЖНО О MOVEMENT_PATTERN
===========================

Не пытайся назначить movement_pattern каждому упражнению любой ценой.

Если упражнение является изолированным движением, для которого нет подходящего паттерна в taxonomy:

`movement_pattern: null`

может быть корректным решением.

Не заменяй `null` на приблизительный паттерн только для того, чтобы поле было заполнено.

==================================================
9. MUSCLES
==========

Проверить:

`primary_muscles`
`secondary_muscles`

по taxonomy.

Не добавлять мышцы только на основании общих знаний.

Использовать данные файлов.

Если исходные данные позволяют однозначно исправить ошибку — сделать точечную правку.

Если нет — `needs_review`.

==================================================
10. INJURY / WARNING RELATIONS
==============================

Используй `08-injury-warnings.json`.

Проверь:

* какие упражнения имеют injury/warning relations;
* существуют ли соответствующие exercise UUID;
* существуют ли соответствующие injury/warning IDs;
* не потеряны ли связи;
* нет ли битых связей;
* не противоречат ли связи содержимому `risks`.

Если связь существует в актуальном `08-injury-warnings.json`, но отсутствует в итоговой БД:

предложить её добавить.

Если связь существует в итоговой БД, но отсутствует в `08-injury-warnings.json`:

НЕ удалять автоматически.

Сначала определить, является ли она действительно ошибочной.

==================================================
11. USER-FACING TEXT
====================

Это очень важный этап.

Пользователь приложения НЕ должен видеть внутреннюю информацию о структуре БД.

Нельзя оставлять в:

* `technique`
* `benefits`
* `risks`
* `settings`

фразы:

"В исходной записи..."
"В исходных данных..."
"В исходной версии..."
"Требуется уточнить..."
"Требует проверки..."
"отсутствует в справочнике..."
"не найдено в equipment..."
"конфликт оборудования..."
"equipment_strings содержит..."
"в исходной записи указано..."

Это внутренние комментарии.

Их нужно заменить на нормальный пользовательский текст ТОЛЬКО если правильная информация может быть подтверждена файлами.

Пример.

ПЛОХО:

"В исходной записи указан конус, но конкретный тип конуса отсутствует в equipment-справочнике."

ХОРОШО:

"Установите конус сбоку от траектории движения."

Но второй вариант допустим только если использование конуса подтверждено данными.

Если оборудование нельзя определить:

не придумывать.

Пометить `needs_review`.

==================================================
12. `equipment_strings`
=======================

`equipment_strings` должен содержать пользовательские канонические названия оборудования.

Названия должны соответствовать:

`05-equipment-v2-corrected.json`

Не писать туда:

* UUID;
* внутренние ID;
* описания;
* комментарии;
* альтернативные технические названия.

==================================================
13. ALTERNATIVES
================

Проверить все `alternatives`.

Для каждой альтернативы:

* существует ли упражнение;
* совпадает ли название;
* существует ли UUID;
* действительно ли это допустимая альтернатива;
* нет ли ссылки на само упражнение.

Не создавать новые упражнения только ради заполнения alternatives.

Если упражнение существует, но название отличается:

использовать актуальное название из `final2DB-equipment-patched.json`.

==================================================
14. ДУБЛИ
=========

Найти:

* одинаковые упражнения;
* упражнения с одинаковой техникой;
* варианты одного упражнения;
* потенциальные семантические дубли.

Но:

НЕ удалять дубли автоматически.

Для каждого кандидата написать:

`duplicate_candidate`

и объяснить причину.

==================================================
15. STATUS
==========

Проверить `status`.

Если упражнение имеет:

`needs_review`

определить конкретную причину.

Если все проблемы устранены и данные подтверждены:

предложить:

`needs_review → approved`

Если хотя бы одна существенная проблема остаётся:

оставить:

`needs_review`

==================================================
16. ИКОНКИ EQUIPMENT
====================

Используй актуальный список SVG-иконок только для проверки соответствия оборудования.

Проверь:

* существует ли иконка;
* соответствует ли она equipment;
* нет ли оборудования без иконки;
* нет ли очевидно неправильного соответствия.

НЕ заменяй корректные SVG без причины.

==================================================
17. ФОРМАТ РАБОТЫ
=================

Работай в два этапа.

ЭТАП A — АУДИТ.

Сначала НЕ вноси изменения.

Выдай список найденных проблем.

Каждая проблема должна иметь:

{
"type": "exercise_field",
"exercise_id": "...",
"exercise_name": "...",
"field": "...",
"problem": "...",
"before": "...",
"after": "...",
"reason": "...",
"status": "fix"
}

Для оборудования:

{
"type": "equipment",
"equipment_id": "...",
"equipment_name": "...",
"problem": "...",
"before": "...",
"after": "...",
"reason": "...",
"status": "fix"
}

Для exercise-equipment relation:

{
"type": "exercise_equipment_relation",
"exercise_id": "...",
"equipment_id": "...",
"action": "add",
"reason": "...",
"status": "fix"
}

Для injury relation:

{
"type": "injury_relation",
"exercise_id": "...",
"injury_id": "...",
"action": "add",
"reason": "...",
"status": "fix"
}

Для неоднозначной проблемы:

{
"type": "...",
"exercise_id": "...",
"exercise_name": "...",
"field": "...",
"problem": "...",
"reason": "...",
"status": "needs_review"
}

ЭТАП B — PATCH.

После завершения полного аудита НЕ переписывай всю БД.

Сформируй только список точечных изменений.

Каждое изменение должно иметь:

* файл;
* объект;
* UUID;
* поле;
* было;
* стало;
* причину.

* консистентной;
* пригодной для приложения;

* с каноническим equipment;
* с корректными exercise-equipment relations;
* с корректными taxonomy values;
* с перенесёнными injury/warning relations;
* без битых ссылок;
* без самовольного удаления данных;
* без выдуманных сущностей;
* без массового переписывания существующей БД.

==================================================
22. ФИНАЛЬНЫЙ ОТЧЁТ
===================

После аудита выдай только:

1. количество проверенных упражнений;
2. количество найденных проблем;
3. количество готовых точечных исправлений;
4. количество `needs_review`;
5. количество проблем equipment;
6. количество exercise-equipment relation проблем;
7. количество taxonomy проблем;
8. количество injury relation проблем;
9. количество проблем пользовательского текста;
10. количество duplicate candidates.

Формат:

{
"audit": {
"exercises_checked": 0,
"issues_found": 0,
"fixes_ready": 0,
"needs_review": 0,
"equipment_issues": 0,
"exercise_equipment_issues": 0,
"taxonomy_issues": 0,
"injury_relation_issues": 0,
"user_text_issues": 0,
"alternative_issues": 0,
"duplicate_candidates": 0,
"icon_issues": 0
}
}

НЕ выдавай полную переписанную БД на этапе аудита.

Сначала нужен полный аудит и точечный patch list.

Только после отдельной команды можно применять исправления.
